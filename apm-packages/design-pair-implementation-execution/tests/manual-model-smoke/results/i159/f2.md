- Material version: DP-T01@1

- Presented at: Assistant response `DP-PRESENT-01`

#### Decision question and why it is needed

Decide where raw Retry-After input is decoded and where the valid-value-versus-fallback choice is owned. `RetryPolicy.GetDelay()` currently has no input and always returns its constructor-provided `fallbackDelay`, while `RetryingClient.WaitBeforeRetryAsync(CancellationToken)` is its only production caller. Supporting missing and invalid server text requires a new boundary contract; the owner determines whether invalidity and fallback semantics remain testable in `RetryPolicyTests` alone or become caller behavior.

#### Facts, constraints, and options

- `src/RetryPolicy.cs`, `RetryPolicy.GetDelay`: owns `fallbackDelay` and currently decides the delay, but has no server-value input.
- `src/RetryingClient.cs`, `RetryingClient.WaitBeforeRetryAsync`: calls `retryPolicy.GetDelay()` and passes the resulting `TimeSpan` plus the original `CancellationToken` directly to `Task.Delay`.
- `tests/RetryPolicyTests.cs`: directly constructs `RetryPolicy` and verifies fallback through `GetDelay`; there are no client tests, mocks, fixtures, DI registration, factory, startup path, or HTTP/header abstraction.
- Repository symbol search found one production call to `GetDelay` and no call sites for `WaitBeforeRetryAsync`.
- The plan's initial proposal favors policy-owned parsing but explicitly says it is not a confirmed Design Pair decision.

| Option | Facts / constraints supporting it | Trade-off and impact on the decision |
| --- | --- | --- |
| A. Pass nullable raw text to `RetryPolicy.GetDelay`; policy parses and chooses server or fallback delay. | Extends the component that already owns fallback selection; existing policy test seam can cover valid, missing, invalid, and negative input without a new client test architecture. | `RetryPolicy` learns the wire-level Retry-After delta representation. `RetryingClient` remains a thin cancellation-aware delay caller. |
| B. Parse raw text in `RetryingClient`; pass a nullable/validated duration to `RetryPolicy` or choose the fallback in the caller. | Keeps transport text outside `RetryPolicy`. | Splits or moves fallback semantics away from their current owner, requires caller-level invalid-input coverage, and introduces a typed intermediate contract despite no existing header abstraction. |

#### Non-binding proposal, unknowns, and validation

- Non-binding AI proposal: Option A. It follows the upstream initial position, keeps fallback and validity behavior in one symbol, and uses the existing focused test seam. This proposal is not locked.
- Open questions: Whether you prefer transport independence enough to move parsing to the caller. There is no uninspected wiring or second caller that would resolve this from repository evidence.
- Expected modification or verification: update `RetryPolicy.GetDelay` and `RetryingClient.WaitBeforeRetryAsync` consistently; extend `RetryPolicyTests` for server and fallback paths.
- Validation expectations: a valid decoded delay reaches `Task.Delay`; missing/invalid/negative input returns the configured fallback; `WaitBeforeRetryAsync` continues to pass its received `CancellationToken` to `Task.Delay` without replacement or suppression.

### DP-T02

- Material version: DP-T02@1
- Evidence revision: `ae4679b7419b59c5aa93f4ac783e50f8a8dd790c`; scoped files clean before handoff creation
- Presented at: Assistant response `DP-PRESENT-01`

#### Decision question and why it is needed

Decide the lexical and numeric validity rule for a Retry-After delta. The plan binds behavior for valid non-negative, missing, invalid, and negative input but does not state whether decimal/fractional values, signs, surrounding whitespace, or values beyond `TimeSpan` capacity are valid. That choice directly controls when fallback is used.

#### Facts, constraints, and options

- No parser exists in the repository.
- The plan asks specifically for a Retry-After "delta", not an HTTP-date, and scopes tests to server delay and fallback behavior.
- `TimeSpan.FromSeconds` can fail for values outside its representable range; successful numeric parsing alone therefore does not guarantee a usable delay.
- No culture, serialization, or public protocol policy exists elsewhere in the repository.

| Option | Facts / constraints supporting it | Trade-off and impact on the decision |
| --- | --- | --- |
| A. Accept non-negative decimal integer seconds that convert safely to `TimeSpan`; use fallback for all other text, including negatives and overflow. | Matches the conventional Retry-After delta-seconds shape and the plan's explicit negative/fallback cases. | Intentionally rejects fractional seconds and duration formats; implementation must make overflow a fallback rather than an exception. |
| B. Accept a broader numeric or duration syntax while still rejecting negatives and overflow. | Could accept more producer formats. | Broadens the public behavior beyond the plan, raises culture/format questions, and risks treating malformed Retry-After values as valid. |

#### Non-binding proposal, unknowns, and validation

- Non-binding AI proposal: Option A, with culture-independent integer parsing and safe conversion. It is the narrowest behavior consistent with Retry-After delta-seconds and gives deterministic fallback semantics.
- Open questions: Whether interoperability with a known producer requires fractional or nonstandard duration text. No such producer or requirement appears in the repository.
- Expected modification or verification: parsing/conversion in the owner chosen under DP-T01; tests for a valid positive value, zero, missing input, malformed text, a negative value, and an unrepresentable value.
- Validation expectations: accepted input returns the exact seconds as `TimeSpan`; every rejected input returns exactly the configured fallback and does not throw.
