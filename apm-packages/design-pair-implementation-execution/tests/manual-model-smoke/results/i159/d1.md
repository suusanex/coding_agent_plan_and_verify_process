### DP-T01: Policy input, parsing, and fallback boundary

- Material version: DP-T01@1
- Evidence revision: clean worktree at `574120d`; `src/RetryPolicy.cs`, `src/RetryingClient.cs`, and `tests/RetryPolicyTests.cs`
- Presented at: Initial Design Pair response to the user request dated `2026-11-11T17:37:21.091+09:00`

#### Decision question and why it is needed

`RetryPolicy.GetDelay()` currently returns only its private configured `fallbackDelay`. Meeting the plan requires a new input and one owner for classifying a supplied delta as valid, missing, invalid, or negative. The decision is whether the policy sees the raw server text and owns both parsing and fallback, as the initial proposal suggests, or receives a parsed nullable delay and owns only fallback selection.

#### Facts, constraints, and options

- `src/RetryPolicy.cs` is the only delay-policy implementation. Its constructor owns `fallbackDelay`, and `GetDelay()` has no parameter.
- `src/RetryingClient.cs` calls `retryPolicy.GetDelay()` once immediately before `Task.Delay`.
- `tests/RetryPolicyTests.cs` directly constructs the policy and asserts its returned delay; this is the existing seam for server/fallback cases.
- No HTTP response/header type, serialization shape, DI registration, factory, or configuration binder exists in the repository.
- The acceptance criteria define a valid **non-negative Retry-After delta** and fallback for missing, invalid, or negative input. For a raw HTTP-style delta, strict non-negative integral seconds avoid accidentally accepting date or culture-specific `TimeSpan` formats. Overflow must also fall back rather than throw.

| Option | Facts / constraints supporting it | Trade-off and impact on the decision |
| --- | --- | --- |
| A. Policy accepts raw nullable text, strictly parses non-negative integral seconds, and returns fallback on null/blank/malformed/negative/overflow input | Matches the upstream initial position; keeps all acceptance classifications in `RetryPolicy`; tests can directly cover every case | Expands the policy from delay selection into protocol-value parsing and establishes `string?` as its input contract |
| B. Caller parses to `TimeSpan?`; policy chooses parsed non-negative value or fallback | Keeps the policy independent of text/protocol syntax | Splits acceptance behavior across caller and policy, requires caller-level parsing tests, and diverges from the upstream initial proposal |

#### Non-binding proposal, unknowns, and validation

- Non-binding AI proposal: Option A. Use strict invariant integer delta-seconds semantics rather than `TimeSpan.TryParse`; it best matches the plan’s “Retry-After delta,” gives `RetryPolicyTests` a single behavioral seam, and turns all invalid forms into the required fallback.
- Open questions: The plan does not explicitly name the raw value type or whether HTTP-date Retry-After values should be supported. HTTP-date support would broaden scope beyond the stated delta criterion.
- Expected modification or verification: Change `RetryPolicy.GetDelay`; add policy tests for valid zero/positive delta plus missing, malformed, negative, and overflow fallback. `RetryingClient` follows mechanically under DP-T02.
- Validation expectations: A valid non-negative delta maps exactly to seconds; all invalid classes return the configured delay without throwing; existing fallback-only behavior remains available through the selected caller contract.

### DP-T02: Caller API and cancellable wait

- Material version: DP-T02@1
- Evidence revision: clean worktree at `574120d`; `src/RetryingClient.cs`, `src/RetryPolicy.cs`, and absence of in-repository call sites
- Presented at: Initial Design Pair response to the user request dated `2026-11-11T17:37:21.091+09:00`

#### Decision question and why it is needed

`RetryingClient.WaitBeforeRetryAsync(CancellationToken)` has no way to supply a server value. The caller contract must expose that value before it delegates delay selection to the policy. At the same time, cancellation must continue to reach `Task.Delay`; parsing or fallback must not consume or replace the token.

#### Facts, constraints, and options

- `RetryingClient` receives `RetryPolicy` through its primary constructor and owns the asynchronous wait, not the delay decision.
- `WaitBeforeRetryAsync` currently passes the caller's token directly to `Task.Delay`, which is the cancellation invariant.
- There are no direct call sites, startup registrations, factories, mocks, or caller tests in the repository. The public method itself is therefore the only visible compatibility surface.
- The repository has no project manifest or HTTP abstraction. Introducing `HttpResponseMessage` or `RetryConditionHeaderValue` would add coupling not required by the plan; a raw nullable value is the bounded integration seam if DP-T01 Option A is selected.

| Option | Facts / constraints supporting it | Trade-off and impact on the decision |
| --- | --- | --- |
| A. Add a raw-value overload and keep `WaitBeforeRetryAsync(CancellationToken)` delegating with no value | Preserves the existing fallback-only public call shape and makes server-aware use explicit; both paths keep direct token propagation | Adds a small overload and delegation path |
| B. Replace the method with `WaitBeforeRetryAsync(string?, CancellationToken)` | Smallest implementation and there are no repository call sites to migrate | Breaks the currently visible public signature and makes fallback-only callers pass `null` |
| C. Pass an HTTP response/header object | Could model protocol integration at the caller boundary | No such abstraction exists in the fixture; adds framework coupling and exceeds the evidence in the plan |

#### Non-binding proposal, unknowns, and validation

- Non-binding AI proposal: Option A if DP-T01 accepts raw text. Preserve the existing method as a fallback-only overload and delegate to a new `string?` overload; both ultimately call `Task.Delay(selectedDelay, cancellationToken)`.
- Open questions: External consumers are not represented in the repository, so compatibility value is inferred only from the existing public method. If signature replacement is explicitly acceptable, Option B is simpler.
- Expected modification or verification: Change `RetryingClient.WaitBeforeRetryAsync`; policy return-value tests provide the focused timing selection seam. A cancellation-focused test is warranted only if the available build/test harness can observe the async method without real-duration flakiness.
- Validation expectations: The exact token reaches `Task.Delay`; an already-canceled token cancels the returned task; missing/invalid server input selects fallback rather than bypassing cancellation.
