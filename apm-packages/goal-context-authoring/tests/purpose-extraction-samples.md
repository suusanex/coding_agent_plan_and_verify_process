# 中心目的の抽出：生成結果のスポット確認

## 入力

以下は公開用に作った架空の会話。A は報告された失敗と同じ条件（最初に目的があり、後半は手段の話が続く）を再構成した。元 Issue 作成前の会話原文ではない。B～D は別題材とし、どの入力にも期待出力や正解例を加えない。

### A：先に目的があり、後半に機能の話が続く

```text
利用者：自分の開発活動全体を継続して相談したい。何のために今これをしていて、状況が変わったら次に何をするか、前回の判断を毎回説明し直さずに見直したい。
相談相手：案件の状態はどこから読む？
利用者：既存の案件台帳から読み取ることにする。
相談相手：案件一覧や優先順位順の表示も作れそう。判断を Memory に保存する方法もある。
利用者：画面や保存先はまだ決めない。案件Aが止まったときには、前にBを保留した理由も踏まえて次を相談したい。この内容でまとめて。
```

### B：元の目的を取り消さずに成果を追加する

```text
利用者：貸出品をいつ返せばいいか、借りた本人が迷わないようにしたい。
相談相手：貸した時の期限が分かれば足りますか。
利用者：延長が認められたら、今どの期限が有効かも本人に分かるようにしたい。
相談相手：延長を申請しただけのときと認められたときも区別できるようにする？
利用者：はい、それも必要。メールで知らせるかはまだ決めない。これでまとめて。
```

### C：同じ入力から異なる二つの達成判定が成り立つ

```text
利用者：会議の後に決定を探せないことと、決定した仕事が終わったか分からないことの両方に困っている。
相談相手：決まった理由を後から読めることと、実行漏れを発見することでは、片方だけを満たすものもありそうですね。
利用者：今回の作業で引き受けるのはどちらか一方です。この話をまとめてください。
```

### D：長い構想検討から新しい仕組みの責務を初めて定める

```text
利用者：しばらく相談してきた展示会の準備室の案を、新規 Issue にまとめよう。これまでのメモを貼るね。
初回：会場の係から「変更を聞いていなかった」と連絡が来た。
次の相談：出展者への時間変更はメールで伝えている。入口の掲示には以前の時間が載っていた。
会場との打ち合わせ：途中から入った係はどの連絡を読めばよいか迷った。連絡係は個々の質問にその都度答えた。
相談相手：共通の予定表と、お知らせをまとめる窓口を作る案がある。
利用者：予定表には既存のものを使う。掲示の仕方はまだ選ばない。以上が相談メモです。
```

D の確認に答える場合の追加発言（独立した模擬応答であり、人間の承認記録ではない）：

> 利用者：対象は会場係だけです。変更のたびに、途中参加の係も今有効な予定を自分で確かめられることが目的です。出展者への告知は今回の対象外です。
