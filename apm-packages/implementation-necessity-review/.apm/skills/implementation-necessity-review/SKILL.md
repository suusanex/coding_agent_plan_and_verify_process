# 実装必要性レビュー

利用者がこのレビューを依頼したときだけ実施する。PRの有無を問わず指定された対象を調べ、結果を報告する。修正は別の依頼で扱う。

1. 要求、利用場面、適用される開発原則から、何が揃えば一件を正しく完遂できるかを把握する。私用ツールでは機能成立と利用時の負担を重視する。実際の失敗を記録して停止する原則を、処理できる入力を異常とみなす理由にしない。
2. 入口から結果を利用する箇所までたどる。拒否・停止・保留、固定上限、形式の厳密一致、復旧処理や状態の更新を起点に、共通関数の呼出し元と後続操作を確認する。個別の不一致が計画全体や別の操作を止める経路にも注意する。必要に応じて差分外のコード、プロンプト、設定、schema、テスト、履歴、外部契約に広げる。全ファイルの投入や一律の探索上限は設けない。
3. 条件に該当しても正しく完遂できる具体例を通し、条件を外したとき実際に失う要求を探す。テストとの一致だけで必要性を認定しない。対象識別、二重実行防止、更新整合性、明示予算など、除去で破れる保証を確かめる。必要性が不明なら不明点を示す。
4. 各指摘にコード位置、入口から生じる影響、具体的な正常利用、不要性の根拠、最小の変更と維持する条件を記す。機構を取り除くと付随する検査や復旧も消えるか検討する。一部に必要なら適用範囲を狭めるか、その条件を解釈する既存処理に任せる。代替の設定・警告・監視・リトライを当然の前提にしない。指摘がない場合も調べた経路と未確認範囲を簡潔に示す。
