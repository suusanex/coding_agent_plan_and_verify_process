# Solution Shape 表現例

以下の見出し、表、箇条書きは表現方法を示すための**一つの仮の設計案**であり、特定の実現方式の推奨や下流の必須フォーマットではない。案件の性質や大きさに合わせて短縮または組み替えてよい。

## 例 1: 複数の実現主体・共有部分を持つ構成（共通 Bot 基盤の仮案）

`suusanex/grok_bot_core_observe_and_improve#23` を題材に、複数の Bot 用途で一部基盤を共有する場合の仮の構成スケッチ例。

### 構成・責務配置

実際の実現主体は次の 5 つとする。

| 実現主体 | 担う論理責務 | 主な関係 |
| --- | --- | --- |
| Grok Bot（ホスト / 対話 UI） | ユーザー対話の受付・送信、対話 UI 固有連携 | 入力を共通実行ホストへ渡し、送信結果と成否を返す |
| 共通サイクル実行ホスト（単一 CLI） | 一巡の進行制御、必要文脈の抽出、差分保存、Git 公開 | Bot 定義に応じて必要な処理を選び、保存と公開を実行 |
| 外部 AI CLI（推論主体） | 意味判断、質問・推薦生成、更新すべき意味差分の作成 | 実行ホストから必要な文脈を受け取り、判断結果と差分を返す |
| Git リポジトリ | 共有関心、Bot 個別記憶、根拠原文、操作履歴の保存先 | 共通ホストが読取り・差分書込み・公開を担当 |
| Notion（ゲーム Bot 固有連携） | 非同期質問と回答の入力・表示画面 | ゲーム Bot 経路から参照・更新する |

### 機能配置

| 機能 | 担当・実現方式 | 重要な制約・共通と固有の境界 |
| --- | --- | --- |
| 一巡の進行と Bot 切替 | 共通ホストが Bot 定義（利用情報源・操作・推論要否）を見て進行する | 共通ホストは進行と保存を扱い、記憶形式・Notion 連携・段階定義は各 Bot 固有設定に閉じ込める |
| 意味判断と推論 | 判断が必要な経路で共通ホストが外部 AI CLI を 1 回呼び出す | 感想記録のみの経路は共通ホストの機械保存だけで完結させる |
| 記憶・状態更新 | AI は意味差分を返し、共通ホストが対象箇所のみ反映する | 既存の記憶・原文・操作成否を維持したまま差分を適用する |
| 変更の Git 公開 | 共通ホストが保存後にコミットと通常 push を行う | 競合時は未公開変更を保持したまま停止・報告する |

### 代表的な実行経路

1. **感想記録の経路（ニュース・X 推薦 Bot）**
   - `Grok Bot UI` が感想を受領 → `共通ホスト` が該当フィードバック差分を `Git リポジトリ` へ機械保存 → 通常 push して完了。
2. **判断を伴う通常一巡の経路**
   - `共通ホスト` が対象 Bot の状態と共有関心の必要範囲を読込み → `外部 AI CLI` を 1 回呼び出し判断結果・必要操作・意味差分を取得 → `共通ホスト` が固有連携（例: ゲーム Bot の Notion 更新や送信）の結果を確認し記憶差分を保存 → 通常 push して完了。

### 重要な違いがある代案（必要な場合のみ）

- **記憶更新の実現方式**: AI が記憶ファイル全文を書き換えて返す案 vs AI は意味差分だけを返し共通ホストが反映する案。
  - 後者は無関係領域の全文再生成や意図しない上書きを避け、感想記録のような差分保存経路も同じ保存処理で扱える。

## 例 2: 少量の入力を一度処理して終わる小さなツール

1 件の設定値をローカルファイルへ保存する小規模 CLI の仮案。この規模では数行の箇条書きで十分である。

- **構成・責務配置**: `単一 CLI プロセス`（引数解析・1 件更新・一時ファイル置換）と `設定ファイル 1 つ`（ローカル保存先）で構成する。
- **機能配置**: 指定キー 1 件の値だけをメモリ上で更新し、既存エントリを保ったまま一時ファイル書き出しと原子的置換で反映する。
- **代表的な実行経路**: CLI 引数（キー・値・ファイルパス）を受領 → 設定ファイルを 1 回読込む → 該当キー 1 件を更新 → 一時ファイル経由で 1 回書き出して終了。
