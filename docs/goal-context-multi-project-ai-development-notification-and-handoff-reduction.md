# Goal Context: 複数AI開発作業の完了通知と手動引き継ぎ負担の削減

> This document is for purpose-achievement review, not exhaustive specification checking. Judge the implementation primarily against the original problem and desired user-visible outcome.

## Original problem

複数のソフトウェアプロジェクトで、ChatGPTによる目的・制約・MVP境界の検討、GitHub Issue作成、Codexでの実装、Pull Request作成、GitHub Copilotレビュー、独立したAIによる目的達成レビュー、Codexでの修正という流れを並行して進めている。

この運用では、人間がCodex、GitHub、ChatGPTなど複数のアプリやWebサイトを順番に見回り、完了した作業を探し出さなければならない。完了した実装を見つけた後も、対応するPRやレビュースレッドを探し、「pushしたので目的を満たしているかレビューしてください」と伝え、レビュー後には再び実装スレッドを探して指摘を渡す必要がある。

人間が複数作業の監視役と、実装側・レビュー側の間のメッセンジャーを兼ねていることが、最も大きな負担である。単に各工程をAI化しても、完了確認、戻り先探索、情報の受け渡しが人手のままなら、複数プロジェクトを並行する際の認知負荷は十分に減らない。

これまでの実装では、この問題を「固定したImplementation ThreadとReview Threadの間でレビューサイクルを管理する問題」と捉えたため、専用プロンプト、thread ID、artifact path、result reference、複数のGoal Context確認ゲートなどを利用者が扱う構造になった。これは、本来減らすべき手順と引き継ぎ作業を別の形式で増やしており、目的を達成していない。

## Desired user-visible outcome

利用者は、複数のCodex作業を見回らなくても、各作業の完了または停止を通知で知ることができる。通知を選択すると、対象となるCodexスレッド、PR、レビュー結果など、その時点で確認または操作すべき正しい場所を直接開ける。

通知を有効にするために、利用者が各プロンプトへDecorator Skillや専用文言を追加する必要はない。通常どおりCodexへ作業を依頼しただけで、作業終了時にはリンク付き通知が行われる。

初回実装の完了後は、通知から元の実装スレッドへ戻り、短い一つの操作で独立レビューと必要な修正を開始できる。レビュー専用のトップレベルスレッドを別途作成・探索し、実装結果やレビュー結果を人間が運ぶ必要はない。

同じ親スレッド内で、実装担当とは分離されたread-onlyのreviewer subagentsがコードと初期検討の目的を評価し、その結果を受けて修正と目的再レビューを行う。利用者は、正常系では実装側とレビュー側の間のメッセンジャーにならない。

## Before and after

### Before

* 利用者が複数プロジェクトのCodexスレッドを定期的に開き、どの作業が完了したかを探す。
* 完了した実装を見つけた後、commit・push・PRの状態を確認し、対応するレビュースレッドを探す。
* レビュースレッドへ実装完了を伝え、目的達成レビューを依頼する。
* レビュー結果を確認し、元の実装スレッドを探して指摘を手動で渡す。
* 修正後も同じ往復を繰り返す。
* プロセスを使うために、専用プロンプト、thread ID、review-plan path、hash、JSON、Goal Contextの状態値などを利用者が扱う。
* 通知機能を使うために、作業ごとにDecorator Skillを指定する。

### After

* 利用者は通常の方法でCodexへ実装を依頼する。
* Codexの作業が完了または停止すると、自動的に通知される。
* 通知を選択すると、対象のCodexスレッドが直接開く。関連するPRや結果がある場合は、それらにも直接移動できる。
* 初回実装後、利用者は同じスレッドで独立レビューと修正を開始する短い操作を一度行う。
* 初回レビューでは、GitHub Copilotのコードレビュー、Codexによる独立コードレビュー、Goal Contextに基づく目的達成レビューを収集する。
* 指摘があれば、同じ親スレッドのagentが既存の実装コンテキストを利用して修正する。
* 修正後は目的達成レビューだけを再実行し、必要に応じて最大3roundまで修正と目的レビューを反復する。
* 完了または人間の判断が必要な状態になると再び通知され、同じスレッドと関連PRを直接開ける。
* 利用者は、トップレベルスレッド間で実装結果やレビュー結果を運ばない。

## Purpose boundaries

* MVPの中心は、すべての開発工程の完全自動化ではなく、非同期に進むCodex作業の完了を見失わず、正しい場所へ直接戻れることと、実装・レビュー間の手動伝言を通常ケースからなくすことである。
* 通知履歴を永続的なタイムラインとして蓄積することは望ましい拡張だが、MVP必須ではない。まずリンク付き完了通知を成立させる。
* 複雑な分岐、長期中断、複数のトップレベル実装スレッド、特殊な手動レビュー運用まで自動制御することは初版の目的ではない。そのようなケースは人間が手動で制御してよい。
* 修正実装は、初版および既定では初回実装を行った親agentが担当する。初回実装時の探索・設計コンテキストを維持し、別の書き込みagentとの調整を避けることを優先する。
* Adaptive Implementation Executionなど、初回実装からsubagentが実装を担当する構成への対応は次の課題である。ただし将来も、別のトップレベルスレッド間で人間が情報を運ぶ構造へ戻すのではなく、同じ親スレッド内で実装executorを差し替えられることが望ましい。
* GitHub CopilotおよびCodexのコードレビューは初回だけでよい。実績上、同じコードレビューを複数回実行しても有益な追加指摘が得られにくいため、修正後に反復するのは目的達成レビューだけとする。
* Goal Contextは初期検討の目的を後続AIへ伝える入力文書であり、複数段階の承認ワークフローや厳格な状態機械を利用者へ課すためのものではない。
* 現在機能しているAPM配布を継続する。今回の目的のためにCodex Pluginへ移行する必要はない。APMからPluginへの移行自体は、必要になれば別の検討課題として扱う。

## Rejected or misleading outcomes

* 「作業が終わりました」とだけ通知し、通知後に利用者がCodex App、リポジトリ、スレッド、PRを再び探さなければならない実装。通知が存在しても、戻り先探索の負担が残るため不十分である。
* 通知を受けるために、利用者がすべての作業プロンプトへDecorator Skillや通知専用文言を追加する実装。通常作業に手順を追加しており、横断的な通知基盤として機能していない。
* Implementation ThreadとReview Threadを固定し、thread ID、review-plan path、Adaptive result referenceなどを利用者がコピーして往復する実装。手動のメッセンジャー作業を別形式で維持している。
* 別トップレベルスレッド間の通信を高度に自動化することをMVPの中心にする実装。通信境界そのものをなくせる通常ケースに対して、状態管理と復旧処理を過剰に増やす。
* Goal Contextを使うために、draft、human-reviewed、sensitive-data review、strict validation、hash確認など複数の手動ゲートを必須にする実装。目的達成レビューの入力を用意する以上の負担を利用者へ課している。
* 各roundでGitHub CopilotやCodexのコードレビューを繰り返す実装。有益性が低い処理と待機時間を増やし、本当に反復が必要な目的達成レビューを埋もれさせる。
* 配布手段をPluginへ移行すること自体を、この目的の達成として扱うこと。APMで必要な配布ができている限り、配布技術の変更は利用者の見回りや伝言負担を直接解消しない。
* reviewerを親agentの自己評価だけで代替する実装。同じ親スレッド内で処理しても、目的達成レビューは別のread-only reviewer agentが独立した入力から行う必要がある。
* 内部artifactやcycle管理が整合していることだけを成功とする実装。利用者が短い操作で目的の流れを実行できなければ、内部的に正しくても目的未達である。

## Priorities and trade-offs

* 汎用的で高度なマルチスレッド制御より、通常ケースにおける利用者の見回り、探索、伝言、コピー操作を直接減らすことを優先する。
* 完全なプロセス自動化より、利用者が必要な時点で処理を開始し、その後の定型的なレビュー・修正往復を一つのスレッド内でまとめて処理できることを優先する。
* reviewerの独立性は、別のトップレベルスレッドを要求することではなく、別agent thread、read-only権限、PR差分とGoal Contextの直接参照、reviewer生出力の保持によって確保する。
* 初版では親agentによる修正実装を選び、構造と操作を単純にする。Adaptive Implementation対応は、初版の利用体験を壊さずに追加できる境界を残した上で後続課題とする。
* 通知は全Codex作業へ常時適用し、詳細な結果metadataがある場合だけ通知内容を強化する。特定Skillを使わない通常作業でも、最低限スレッドへ戻れる通知を出す。

## Purpose-critical decisions

* Codex作業の完了検出は、各Skillに通知Decoratorを付ける方式ではなく、ユーザー単位のCodex `notify` callbackを使う常時有効な基盤として実現する。
* 通知runtimeとその導入・確認手段はAPMで配布し、ユーザー単位のCodex設定へ一度導入する。日常利用時に通知用Skillを選択させない。
* 一般的なCodex作業ではスレッドへの直接リンクを通知する。対応SkillがPRや判定結果を持つ場合は、同じ通知へPRや実行結果へのリンクを追加する。
* 初回実装後のレビュー・修正は、別のトップレベルReview Threadとの往復ではなく、初回実装を行った同じ親スレッドから開始する。
* 初回レビューではコードレビューと目的達成レビューを行い、修正後は目的達成レビューのみを反復する。
* 目的達成レビューは実装担当とは別のread-only reviewer subagentが行い、親agentの自己申告だけで完了と判定しない。
* 最大3roundで収束しない場合や、目的上の判断を自動で確定できない場合は、人間の判断が必要な状態として停止・通知する。

## Material corrections

* 当初の問題は「実装とレビューのサイクル管理」そのものではなく、複数の非同期AI作業を人間が見回り、正しい作業場所を探し、実装側とレビュー側の間で情報を運ぶ負担である。途中で生じた「固定した二つのトップレベルスレッドを往復させるプロセス」という理解は、この目的を狭めた誤解として撤回された。
* 各roundを新しいスレッドで開始する構造だけでなく、固定した二つのスレッドを人間が交互に再開する構造も、通常ケースでは不要と判断された。独立レビューはsubagentで確保し、手動引き継ぎの境界自体をなくす。
* すべてのレビューを各roundで再実行する案は修正された。コードレビューは初回のみ、反復対象は目的達成レビューのみである。
* 通知Decoratorを各作業で明示する方式は、常時有効な`notify`基盤へ置き換える。
* Codex Pluginを今回の配布・実行基盤として導入する案は採用しない。既存のAPM配布を継続する。

## Unknowns affecting purpose judgment

* [Unknown] Codexの`notify` callbackが親turnだけでなくsubagentの完了にも発火するかは、実環境での確認が必要である。subagentごとに不要な通知が大量発生すると、見回り負担を減らすという目的に反するため、利用者へ提示する通知は親作業の完了・停止を中心に整理されなければならない。
