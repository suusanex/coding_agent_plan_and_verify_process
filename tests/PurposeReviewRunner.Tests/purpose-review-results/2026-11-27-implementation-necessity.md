# 不要性を調べるレビューの比較（Issue #181）

Codex CLI 0.172.0、gpt-6.2-astra、medium、read-only の独立セッションで各条件を1回実行した。評価担当だけが Issue の既知例を参照した。実装レビューには私用ツールの開発原則と対象経路を渡し、作業ディレクトリ内のソースを探索させた。修正案や過去の指摘は入力していない。

## 設計入力

取引IDごとに請求を一度登録し、正しい合計とIDが必要という目的を提示した。案は「抽出CLIはIDと合計のJSONを返し、詳細ログには使った辞書の版を出すことがある。取込側は終了コード、JSON、詳細ログ内の辞書版を照合してから、登録済みIDを除外して記帳する。」とした。

bc8a85d の 0.7.0 と本変更の 0.7.1 の初回 reviewer 指示を抽出し、同じ設計入力を末尾に付けた比較であり、Runner のセッション起動試験ではない。どちらもログが欠けた正常な請求を具体例として指摘し、取引IDによる重複防止を維持した。追加機構の要求はなかった。この例で検出差は観測されなかった。渡したテキストは UTF-8 で 10,121 → 10,047 bytes、CLI 報告のセッション使用トークン数は 24,765 → 17,141。後者は推論等も含み、指示だけのトークン差や一般的な費用削減率を表さない。

## 実装経路

grok_bot_core_observe_and_improve の各版から scripts/bot-runtime を展開し、「Botの判断から返信まで」を調査させた。同じ旧版への通常レビューと、依頼に今回の Skill 本文を添えた場合を比較した。配布クライアントからの起動試験とは別の評価である。

| 対象 | 観測結果と評価 |
| --- | --- |
| b3a43d5・通常 | 未確認返信の再送、履歴解析失敗、配達確認後の表示を指摘。Issue の既知5例は指摘しなかった。 |
| b3a43d5・手動 Skill | Capabilities.cs の検索で片側が有効でも空配列で計画全体が拒否される経路、4項目の取得を個別に渡せるのに全拒否する経路を発見。対象項目の照合と操作IDの一意性を維持する案だった。旧運用の件数方針の廃止まではこの証拠で決められない。判断7回上限、stdoutのモデル名、effort列挙は見落とした。 |
| ca44b162・手動 Skill | 修正済みの空配列・4件上限を再指摘しなかった。記憶更新先が曖昧な場合も返信を分離する案は、一意性検査自体は残す一方、部分成功の管理が必要になる。元の受付単位の整合性を確認できず、改善として採用できない。 |
| 別ドメイン・手動 Skill | 本変更の PurposeReviewRunner の C# ソースだけを渡し、提出と予算管理を調査。新規 change の proposal version 再利用を遮る位置を特定したが、FINDINGS から新規開始する案と残予算中の追加予算を許す案は既存 Skill の明示契約に反する。外部仕様を外した条件での誤指摘で、予算判定の変更根拠にはならない。 |

PR #36 の b3a43d5 のツリーから当該レビューの提出全文と実行 Runner 版の対応は特定できなかった。今回の比較から当時の見落としの原因やリポジトリ全体での検出率は推定できない。
